# 技术难点与实现细节

> 本文记录本项目在实现过程中真正遇到的技术难点、解决思路与取舍，便于面试复盘、项目陈述。核心代码集中在 `app.py`（单文件 Streamlit 应用）。

---

## 1. 中文知识库检索：无分词器的字符 n-gram + BM25

### 难点

知识库是中文学术内容，而中文没有空格分词边界。常见的 jieba 等分词器对材料科学专业术语（如「致密度」「施密特因子」「霍尔佩奇」「临界分切应力」）切分不准，会导致漏召回；同时引入第三方分词依赖会增加部署复杂度。

### 方案

- **字符级 n-gram 分词**：中文按「单字 + 相邻双字」切分（unigram + bigram），英文和数字按连续串整体切分（见 `_tokenize`）。不依赖任何分词器，对专业术语天然鲁棒——「致密度」会被切出「致 / 密 / 度 / 致密 / 密度」等子串，无论检索「致密」还是「密度」都能命中。
- **标题加权**：检索文本 = 标题 × 3 + 正文 + 例题，让「概念名称」对排序的影响更大。
- **BM25 打分**（k1=1.6, b=0.75）取代早期版本用的余弦相似度：BM25 对短查询、长文档的匹配更友好，且自带文档长度归一化，避免长文档天然占优。
- **查询扩展**：维护一张「题型关键词 → 相关术语」表（如「杠杆」→ 杠杆定律 / 相图 / 质量分数 / 相对量 …，见 `SYNONYMS`），命中时把扩展词并入检索词，解决「换个说法就搜不到」的问题。
- **无硬阈值**：不设相似度门槛，保证每次都有上下文喂给模型，避免「检索为空导致模型凭空编造」。

### 权衡

n-gram + BM25 本质是「关键词检索」，语义理解弱于向量检索（embedding）。但在知识库只有 125 张卡片、领域高度集中的前提下，关键词检索**又快、又准、又省钱**（零 embedding 成本、零向量数据库），且结果**可解释**——能说清为什么命中这张卡，这正好服务于本项目的「答案可溯源」目标。

## 2. 让大模型的计算题「算得准」而不是「估得错」

### 难点

大模型做数值计算不可靠。杠杆定律、相组成物/组织组成物这类计算题，让它直接心算往往会给出一个「看起来合理、其实是错的」数字，这在考研复习里是不可接受的。

### 方案：代码执行，而非模型心算

1. **提示词约束**：要求模型遇到计算题时输出一个 ```python 代码块```，用 `print` 把「已知条件 → 公式 → 代入数据 → 计算结果 → 结论」打印成干净、可读的中文（见 `build_prompt`）。
2. **真实执行**：系统用 `subprocess` 运行这段代码，捕获 stdout，然后把代码块**替换**为真实输出（见 `run_calc_code` / `run_python_code`）。
3. **用户看不到代码**：最终用户只看到打印结果，所有数值以代码执行为准。
4. **兜底**：20 秒超时；执行出错时显示错误信息，而不是静默给出错误值。

### 关键点

把「计算」这件事从大模型的概率生成里剥离出来，交给确定性的 Python 解释器。大模型只负责「决定用什么公式、写什么代码」，具体算数由程序保证正确。

### 权衡

模型生成的代码本身可能有 bug，但此时会**暴露错误**（报错信息），比「静默给错答案」更诚实、可排查。这体现了对 LLM 能力边界的清晰认识：**让 LLM 做它擅长的（理解 + 生成），把不擅长的（精确计算）交给程序**。

## 3. 公开部署下的密钥安全

### 难点

项目部署在公开的 Streamlit Cloud，但调用 DeepSeek / Claude / Qwen-VL 需要 API Key。密钥一旦写进代码或提交到仓库，就会泄漏、被盗刷。

### 方案：三层隔离

- **云端**：密钥放在 Streamlit Cloud 的 Secrets 里，代码通过 `st.secrets` 读取，不入库。
- **本地**：环境变量兜底。
- **访客自填**：没配云端 key 的访客可在侧边栏填自己的 key，保存在本地 `.config.json`（已加入 `.gitignore`），不上传、不共享。
- 读取优先级统一封装成 `_env_or_secret()`：先读 `st.secrets`，再读环境变量。

### 效果

仓库里零密钥；作者配 key 时访客免填，没配也不影响「知识地图 / 闯关练习 / 学习记录」等不依赖模型的板块使用。这套「云端 Secrets + 环境变量 + 访客自填」的组合，是低成本公开部署 LLM 应用的常见范式。

## 4. 移动端性能：3D 可视化的懒加载

### 难点

Plotly 的 3D 晶体图较重，直接渲染会让手机首屏卡顿。

### 方案

- 3D 晶体模型默认**不渲染**，用 toggle 开关按需加载（`show_3d`）。
- 铁碳相图默认折叠在 `expander` 里，不主动展开。
- CSS 响应式：媒体查询区分 PC / 移动端，装饰元素在移动端缩小靠边；动画遵循 `prefers-reduced-motion`，用户开启「减弱动态效果」时自动关闭。

### 效果

移动端首屏流畅，3D / 相图等重资源「按需加载」，兼顾展示效果与性能。

## 5. 无题库章节的题目兜底（确定性生成）

### 难点

「闯关练习」依赖 `question_bank.json`，但部分章节没有现成题库，直接「无题可用」体验差。

### 方案

用 `md5(章节名)` 做随机种子，从该章知识点卡片里**确定性**地生成「概念 ↔ 定义匹配」式单选题（见 `_rule_questions`）：同一章节每次生成的题目一致（稳定、可复现），不同章节题目不同。

### 价值

保证任何章节都有可用的自测题，且无需为每个章节手工维护题库——把「题库」和「知识库」打通，知识库扩充后题目自动跟着增加。

---

## 小结

这些难点的共同点，是**围绕大模型的边界做工程**：能确定计算的不交给模型猜、能检索的不让模型凭空编、能本地处理的不引入重依赖、能懒加载的不拖累移动端。这也是本项目在技术上区别于「调个 API 套个壳」的地方。
